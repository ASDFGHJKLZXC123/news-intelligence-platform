## Implemented scope and operating instructions

Phase 4A replaces the personal workflow's queue requirement with a managed Python child. The API and manual command use the same supervisor and reusable business runner. The registered task `workers.personal_tasks.run_personal_daily` remains available for the configured Celery transport and delegates to that runner. Both managed delivery paths rotate the queued delivery token on the actual running claim. Durable processing mode (`legacy` or `personal`) remains separate from delivery transport (`celery` or `subprocess`).

The additive revision is `0023_personal_processing_control`. It expands the existing writer-mode singleton with the global owner, fencing generation, fixed deadlines, and retained launcher/child lifetime history. Supported processing mutations and dispatches verify the current mode and owner. Personal RSS/provider work runs outside business transactions; returned data is fenced again before persistence. Already-dispatched requests retain an accounting-only reconciliation path that cannot write old business results.

The deployed 4A shape is PostgreSQL, Redis, one loopback application process, the existing separate frontend server, and a temporary child for each explicit update. Redis still supplies cache/rate-limit dependencies. Celery worker and Beat are stopped for the recorded child/UI proofs; the application does not start them. Production deadlines remain a two-minute queued handoff, 25-minute graceful deadline, 30-minute hard deadline and 35-minute ownership lease from the actual running claim, with no lease renewal. The child arms its original queued deadline before its first database connection and verifies it against the durable row before claiming.

Use [PHASE4A_SETUP.md](../../PHASE4A_SETUP.md) for the full configuration, startup, recovery and backup instructions. The implemented commands are:

```sh
python -m services.personal.cli mode personal
python -m services.personal.app --port 8000
python -m services.personal.cli start
python -m services.personal.cli retry RUN_UUID
python -m services.personal.cli status
python -m services.personal.cli reconcile-children
python -m services.personal.cli recover RUN_UUID
```

The personal configuration requires `PERSONAL_PROCESSING_TRANSPORT=subprocess`, `PERSONAL_PROCESSING_MODE=personal`, loopback binding and one application process. Mode changes require idle, confirmed processing state. Recovery and polling do not start a new child or reset the total three-attempt limit. Supported runtime rollback is an explicit idle switch to `legacy`, retaining the upgraded schema and data. Older binaries that cannot honor the writer guard are not supported writers against that database.

**Ordinary paid activation remains off.** These proofs use blank provider credentials, explicit synthetic fixtures or scripted transports, and no external provider calls. Selecting the new runtime neither authorizes an allowance nor enables live processing. The Phase 4B Redis removal, local cache/limiter, and single-address frontend are unstarted. P4-10 through P4-12 belong to 4B. Phase 5 relevance/usefulness validation is unstarted.

## Corrections and evidence limits

[Initial worker failure](worker-initial-failure.log) is retained. A meaningful default-session regression preceded the fix to return materialized, detached audit values while preserving the fenced audit transaction. Final actual Celery/child/UI parity succeeds after the correction.

The child bootstrap test reproduced a real deadline bug before the fix: a first PostgreSQL `pg_sleep(60)` query with configured 100-second connect/999,999-ms statement settings outlived its original five-second handoff and still had not exited at seven seconds. [Before proof](runtime-bootstrap-before.log) is retained. The child now arms the original supervisor-read deadline before its first connection, caps bootstrap DB bounds at 3/5 seconds, and verifies exact durable deadline equality. The stable test kills the blocked child about 71 ms after its original handoff, without a running claim or provider call.

Tests also preceded the registered Celery token-rotation fix and remaining-budget/Redis/RSS/late-paid-accounting corrections. Those are harness failures, not four or two runtime defects. The intermediate source-drift lifecycle run likewise does not indicate a resource or runtime failure.
